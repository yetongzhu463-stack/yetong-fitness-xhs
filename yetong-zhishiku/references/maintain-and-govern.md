# 维护与治理

## 局部更新

1. 从当前对话确定条目、目标路径或已确认版本；有歧义只问更新对象。
2. 读取导航和直接相关资料；路径修正核对新位置，版本变化核对依据。
3. 先判断能否修改已有主题入口，不为普通附件新增顶层记录。
4. 检查已有授权和现场内容，只改对应条目。写入前核对目标内容未漂移。
5. 核对 diff 和新路径，交实际变化清单。

不扫描全库，不重写整份导航，不修改 Agent 入口，不顺手移动资料，不重复首次使用引导。发现相关冲突时只扩大到解决该冲突需要的资料；发现无关问题可简短记录，不自动修复。

## 只读健康检查

先结构和路径，再按问题下钻：

- 导航入口是否可达，主要资料领域是否缺入口。
- 是否有无解释的多个当前版本、职责重叠、悬空引用或历史资料误列当前来源。
- 待整理和根目录是否积累无归属资料；判断“长期”“大量”时给实际观察，不套统一阈值。
- 当前 Agent 的调用入口是否存在、是否重复；未知宿主机制保留为未验证。
- 重复文件只凭实际证据报告；同一链接多次出现不等于重复业务文件。

脚本只能提供其覆盖范围内的结构证据；内容权威、业务冲突和领域覆盖继续看原资料。输出立即处理、建议处理、保持现状及范围；只读任务不能附带修复。

## 导航治理

### 启动条件

用户提出瘦身、分层、优化导航，或发现逐文件登记、重复、失效入口、敏感明细及大量无关条目影响定位。大小和行数只是观察指标，不是单一触发阈值。

### 读前基线

统计导航行数、UTF-8 字节数、表格非分隔行（含表头）、识别到的本地引用、唯一目标和失效项。记录脚本版本、覆盖范围和统计口径；不要把引用次数说成全库文件数。

按最密集主题下钻，列出保留、合并、下沉、修复范围和候选承接 README，先核对职责与版本。方法依据：层级信息架构与变更控制。

### 处理

- 保留目录职责、主入口、必要动态状态、权威与冲突规则、跨目录关系和少量高频直达文件。
- 同项目合并为一个主入口，写清范围、状态、业务时效与局部索引。
- 附件、原始表、过程稿、历史和同类清单下沉局部索引；不因此移动原件。
- 移除导航中的重复或已被覆盖条目，不删除原始业务文件；失效但业务意义未知的入口先标明待确认，避免直接丢失。
- 原有局部索引可用则复用；敏感内容仅留安全目录或说明入口。
- 证据不足的版本冲突继续保留，不为“整洁”指定唯一答案。

### 变更与验证

1. 展示修改路径、承接关系、保留内容、备份和原件／入口影响；已有授权足够就继续，缺决定才补问。
2. 写前保存原导航和被修改的局部索引到已有安全备份目录，或 `.trash/` 中以日期及可区分版本命名；不覆盖旧备份。备份不列为当前入口。
3. 记录各目标读入版本，写前再核对；漂移时重读合并，停止旧版本覆盖。
4. 按最小范围修改，随后检查路径存在、关键入口覆盖、版本与冲突保留，以及原件和无关规则未变化。
5. 每项关键事实仍应直达或经一层局部索引到达；动态结论继续核对原文。路径有效不等于事实核实。
6. 失败时停后续步骤，说明完成部分、未完成部分与备份；恢复前确认目标仍是自己写入的版本，不覆盖后来改动。
7. 用同一口径报告前后指标。减少比例使用“前减后，再除以前”；前值为 0 时不计算比例。查找完整性优先于压缩率。

## 防止再次膨胀

一个项目默认一个顶层入口，内部附件由局部索引承接。只有权威来源、职责、版本关系或高频入口变化时更新顶层。轻量更新优先修改已有主题；健康检查同时看重复、失效和索引覆盖，不以目录整齐代替可用性。
